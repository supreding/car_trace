  接口文档    /data/car-trace/app/API接口清单.md（第一节约可直接发给对接方）

  服务管理（SSH 到服务器后）：
    systemctl status  car-trace            # 查询服务（80 端口，开机自启）
    systemctl restart car-trace
    journalctl -u car-trace -f

  定时流水线（systemd 定时器，每 30 分钟自动跑一次，2026-09-21 起由每日 03:00 改为每半小时）：
    备份数据库（/data/backups/，保留 7 份）
    → 全园区照片同步（自动发现 data/ 下新园区）+ OCR
    → GPU 流水线（只处理新增/未处理的抓拍）
    → 收尾：未关联货车归类 → 大门照片重归类 → 共用大门去重 → 车辆重聚
    无新增图片时自动跳过 GPU（状态记为 SKIPPED）。
    cat  /data/pipeline_status.txt          # 最近一次结果
    systemctl start car-trace-pipeline      # 手动立即触发
    journalctl -u car-trace-pipeline -f     # 运行日志

  新园区接入：照片放 /data/car-trace/data/<园区名>/<月份照片根>/<日期>/<订单号>/，
  等定时器自动处理（每 30 分钟，或手动触发）；页面园区下拉框自动出现，无需改配置。

  共用大门跨园区去重（多园区共用同一大门时必开）：上游会把同一张抓拍照片写进
  每个园区的目录树（文件名一致，新版命名末尾带唯一id），同一辆车被多个园区计入。
  流水线在重归类之后自动判重，规则分两类：
    - 新命名（末尾唯一id，如 出磅2026年11月5日08：15：59_2346200）：id 全等直接判
      同一事件；id 不同即同秒不同车，绝不合并；
    - 旧命名（无id，存量多数）：同 (阶段+拍摄秒) 只是疑似，必须文件字节一致
      （MD5）才判同一事件——不同车不可能字节相同，旧数据重跑零误杀；
      文件不在盘（归档已清理）无法确认时跳过。
  每组按证据强制仲裁唯一赢家（真实订单 > 车牌锚定 > 行程时间线 > 外观 > 时间就近
  > 编号），落败副本移入 data/重复抓拍隔离-<原园区>/...（每个原园区一个隔离园区，
  页面与开放接口不显示，文件共享里可按园区查看），全部写 gate_dedup_log 日志：
    python app/build_db.py --dedup-gate              # 试运行（只报告不动数据）
    python app/build_db.py --dedup-gate --apply      # 真正隔离
    python app/build_db.py --undo-dedup              # 全部撤销；--capture-id N 单张撤销
  阈值可环境变量覆盖：GATE_DEDUP_SIM_MARGIN（外观领先幅度，默认0.03）、
  GATE_DEDUP_TIME_MARGIN（时间就近差距秒数，默认300）、GATE_DEDUP_SEQ_MAX_HOURS
  （行程时间线窗口小时，默认12）。
